# 按得分要点阅卷：设计

状态：已定稿（2026-11-16），第 10 节的待定项都按建议定下。基于 main `bcdde29`（0.3.0）。按第 9 节分期实现，A 期还没开始。

## 1. 现状

- 评分标准是一段自由文本（任务的 `majorInput.content`，在面板「题目设置」里填）。没有结构化的要点列表。
- 第二阶段提示词让模型「根据题目、参考答案和评分标准」打分，并输出 `points`：每点 `rubric`（如「①」）、`level`（full / partial / none）、`delta`、`quote`。服务端校验 `quote` 必须能在转录文字里找到，再把各点 `delta` 相加、按步长取整，得出总分（`server/src/judge/model.service.ts` 的 `parseVerdict`）。
- 问题：
  1. 要点是模型每次自己从文本里拆的。同一道题，这份拆成 3 点，下一份拆成 4 点，标号和分值都可能不一样，没法逐点比较。
  2. 逐点结果只写进了 trace，评分记录（`judge_records`）里没有，返回给扩展的 `GradingInfo` 里也只有拼好的 `reasons` 文字。
  3. 老师确认时只能交一个总分（`ConfirmDto.modifiedScore`），看不出是哪一点改了。
  4. 参考答案和评分标准一起给模型，模型容易拿学生作答去比参考答案的措辞，而不是看是否答到要点。
  5. 手动模式其实也要先点「获取建议分」，才会出现给分界面；没有「不用 AI、老师直接打分」的路径。

## 2. 目标

1. 每道题有一份**老师确认过的得分要点列表**：每点有分值，外加一条汇总规则。AI 负责起草，老师确认后才生效。
2. AI 评分以要点为主要依据，按固定的要点逐点给分；参考答案只用来帮助理解要点。
3. 评分结果和老师的确认都按要点保存。
4. 面板按要点打分：每点可以给满分、半分、0 分或自定义，总分自动统计。
   - 手动：老师逐点打分，不调用 AI，也不扣次数。
   - 半自动：AI 先给每点打分，老师逐点检查后提交。
   - 全自动：照旧自动提交，但条件更严。
5. 不配要点列表的题，评分流程和现在完全一样。

## 3. 得分要点列表

### 3.1 结构

存在任务上的一个新字段 `rubricPoints`（单独一列，不放进 `question.content`，免得和平台的题目结构混在一起）：

```ts
interface RubricPoint {
  id: string;            // 'p1'、'p2'…；改文字、调顺序都不变，用来对齐历史记录
  label: string;         // 显示用标号，如「①」「要点一」
  text: string;          // 要点句（可以带解释）
  examples: string;      // 标准里「如……」举的典型事例，可空
  score: number;         // 该点分值
  allowPartial: boolean; // 能否给部分分，默认 true
}

interface Rubric {
  points: RubricPoint[];                      // 1 到 12 点
  rule: { kind: 'sum' } | { kind: 'best'; n: number };
  version: number;                            // 修订号：要点列表、汇总规则、任务的满分或步长任一改动都 +1（同一事务）；只增不减，删掉要点列表再新建也接着往上加，不会复用旧号
  basis: string;                              // 生成时依据文本的哈希，用来发现评分标准改过
  confirmedBy: number | null;                 // 老师确认后才生效
  confirmedAt: string | null;
}
```

### 3.2 汇总规则

规则只算出**未封顶**的汇总值，封顶统一在最后一步做：

- `sum`：汇总值 = 各点得分之和。也覆盖「每点 2 分，最多 6 分」这种写法（封顶交给最后一步）。
- `best`：汇总值 = 得分最高的 n 点之和。对应「答出任意三点即可」。
- 计算顺序固定为：汇总值 → 按步长取整 → 夹到 [0, 满分]。和现有 `snapScore` 完全一致，所以结果不会超过满分。例如满分 5、步长 2、三个 2 分的点全对：6 → 取整 6 → 封顶 5；满分 6、步长 5、两个 5 分的点全对：10 → 取整 10 → 封顶 6。
- 封顶后的满分不一定是步长的整数倍（上面的 5 分、6 分）。凡是要求「步长整数倍」的地方，都把**正好等于满分**当作例外（见第 5、6 节）。
- 总分始终由服务端和面板用同一个函数计算，不让模型自己算。

### 3.3 校验（保存时）

- 每点分值大于 0，并且是步长的整数倍。
- `sum`：各点分值之和不能小于满分，否则提示「全部答对也拿不到满分」。大于满分是允许的，说明有多种答法可以得分。
- `best`：n 小于等于点数，且得分最高的 n 点分值之和不能小于满分。

### 3.4 生成和确认

- 新接口 `POST /api/tasks/:id/rubric/draft`：用一次文本模型调用，不带答卷图片。输入是题目、评分标准、评分细则和参考答案，返回一份草稿 `Rubric`，还没确认。
  - 评分标准里已经有「①②③」或「每点 x 分」时，按原文拆，不改写。
  - 只有参考答案时，从参考答案里归纳要点，并标出「由参考答案归纳，请重点核对」。
- 老师在面板的「题目设置」或控制台的任务页修改草稿：改文字、改分值、增删要点、选汇总规则，然后点「确认」，调用 `PUT /api/tasks/:id/rubric` 生效。
- 扩展原来的任务 upsert（`PUT /api/tasks`）不会碰 `rubricPoints`，旧扩展保存题目也不会把要点列表清掉。
- upsert 改了满分或步长时，同一个事务里把修订号 `version` 加一，并用 3.3 的规则重新校验已确认的要点列表。修订号变了，打开在改动之前的「直接打分」表单提交时就会得到 409（第 6 节），不会按老师没看到的满分保存。
  - 仍然合法：照常生效。
  - 不再合法（比如步长从 1 改成 2，1 分的点就不是步长的整数倍了）：upsert 照常成功，因为旧扩展处理不了拒绝；但要点列表退回「待确认」（清掉 `confirmedAt`），不再生效。这道题回到第 4 节之前的旧评分流程，面板和控制台提示「满分或步长改了，要点列表需要重新确认」。
- 评分标准文本改了以后（`basis` 对不上），要点列表照常使用，但面板和控制台会提示「评分标准改过，要点列表可能需要更新」，并提供「重新生成草稿」。

## 4. AI 按要点评分

有确认过的要点列表时，第二阶段的提示词改成按要点打分。第一阶段的纯转录不变。

- 提示词的主体是【得分要点】：逐点列出 `id`、要点句、典型事例和分值。【参考答案】降为「帮助理解要点，不要求措辞一致」。保留现有的「要点句是得分单位、典型事例也算」读法。
- 输出格式：

```json
{"points": [{"id": "p1", "level": "full|partial|none", "score": 2, "quote": "转录原文片段", "why": "一句话理由"}],
 "confidence": 0.8, "comment": "一句话评语"}
```

- 服务端校验，在现有引用校验基础上加几条：
  - 只接受列表里有的 `id`，每个 id 只取一次；模型漏掉的点按 none、0 分补上，并标记 `missing: true`。有漏掉的点时置信度同样下调，而且这份结果不能全自动提交（和引用没通过一样，见第 5 节）。
  - `full` 得该点满分，`none` 得 0。`partial` 取模型给的分，按步长四舍五入后夹到 [步长, 分值 − 步长] 之间，保证结果确实是「部分分」，不会被取整成 0 或满分。
  - 一个点「能给部分分」的前提是 `allowPartial` 为 true **并且** 分值至少是两个步长（比如步长 1 时分值 ≥ 2）。不满足时（`allowPartial` 为 false，或 1 分的点、步长 1）这个点只有 0 和满分，模型给的 partial 按 none 处理。面板、确认校验都用同一个判断。
  - `quote` 校验失败的点按现在的规则不计分，同时降低置信度。
  - 总分用 3.2 的同一个函数计算。
- 多次采样时，逐点比较各次结果：每点记下各次的得分 `samples`，各次得分不全相同就是 `disagree: true`。总分相同但逐点不同（比如两次分别给 p1/p2 打 2/0 和 0/2）也算不一致。不一致的点在面板上标黄，全自动遇到也会暂停（第 6 节）。
- 历史确认的评分示例（自动学习）改成带上每点的得分，让模型学的是每一点的尺度，而不是只学一个总分。
- `PROMPT_VERSION` 升到 5。没有确认过的要点列表的题，继续用版本 4 的提示词。

### 4.1 要点列表改了以后：缓存、并发合并和评分示例

现在同一张图重复评分会直接复用上次的记录（按 `userId + taskId + 图片 sha256` 查），同时进行的同图请求也按这三项合并（`judge.service.ts` 的 `judge()`）。要点列表改版后，这些都要带上修订号，否则会把按旧规则算的结果当成新结果：

- **缓存**：按要点评分时，只复用 `rubricSnapshot.version` 等于当前修订号的记录。版本不同就当作没有缓存，重新评分（照常扣次数）。
- **退回旧流程时的缓存**：要点列表退回「待确认」（3.4）或被删掉后，这道题按旧流程评分。这时只复用**没有 `rubricSnapshot`** 的记录，按要点评出来的记录不拿来当旧流程的缓存，反过来也一样。从来没有要点列表的题，缓存规则和现在完全一样。
- **并发合并**：合并键加上修订号，变成 `userId:taskId:sha256:version`（没有要点列表时 version 记 0）。评分进行中改了要点列表，后来的请求不会拿到按旧版算的结果。
- **评分示例（自动学习）**：只选同一修订号、并且老师按逐点确认过（有 `finalPoints`）的记录作示例，逐点得分一起带上。版本不同、或者只确认了总分的记录不进示例。刚改版时示例会变少甚至没有，这是预期的：宁可没有示例，也不让模型学到按旧规则给的分。

## 5. 保存

`judge_records` 加三列，都可以为空。旧记录不受影响。

- `rubricSnapshot`：评分时那一版要点列表的**完整快照**（要点、分值、`allowPartial`、汇总规则、`version`），再加上当时的满分和步长。任务上的要点列表以后怎么改，这条记录的含义都不变；确认校验和记录详情都只读这份快照。快照只有几百字节，不另建版本历史表。
- `aiPoints`：AI 的逐点结果 `[{ id, level, score, quote, why, verified, missing, samples, disagree }]`。`missing` 表示模型漏判、由服务端补成 none / 0 的点，用来和正常的 0 分区分（重新读取记录或命中缓存时也要保留）。`samples` 和 `disagree` 只在多次采样时有。它们跟着记录保存，同一张图命中缓存时也照样返回，不会丢掉不一致的提示。
- `finalPoints`：老师确认的每点得分 `[{ id, score }]`；老师只改了总分时为空（见下）。

确认接口 `POST /api/records/:id/confirm` 只新增字段，不改原有的：

- `modifiedScore` 从必填改为「和 `points` 至少传一个」，其他校验不变。旧扩展一直会传 `modifiedScore`，不受影响。
- 服务端开着 `forbidNonWhitelisted`（`server/src/main.ts`），不认识的字段会直接返回 400，所以**不能**靠「旧服务端忽略 `points`」来兼容。改为按服务端能力决定发什么：
  - 这条记录的 `GradingInfo` 带有 `rubric`（只有支持要点评分的服务端才会返回）时，扩展发 `points` 加上自己算出的 `modifiedScore`。
  - 没有 `rubric` 时（旧服务端，或这道题没有要点列表），只发原有的 `modifiedScore` 和 `isAuto`，面板也不显示逐点区。
  - 「直接打分」同理：只有任务信息里带 `rubricPoints` 时才显示这个按钮。
- 新增可选的 `points: [{ id, score }]`。传了 `points` 时，服务端按这条记录的 `rubricSnapshot` 校验并重新算总分（要点列表在评分之后改过也一样，用的是快照）：
  - id 必须都在快照里，每个 id 最多一次；没传的点按 0 分。
  - 每点得分在 0 到该点分值之间，并且是步长的整数倍；`allowPartial` 为 false 的点只能是 0 或满分。
  - 同时带了 `modifiedScore`，但和算出的总分不一致：返回 400。
- 只传 `modifiedScore`、不传 `points`：和现在一样只存总分，`finalPoints` 留空。旧扩展、以及老师手动覆盖总分时都走这条。
  - 记录**带 `rubricSnapshot`**（按要点评的）：`modifiedScore` 要在 0 到满分之间，并且是步长的整数倍；正好等于满分时例外（满分可以不是步长的整数倍，见 3.2）。
  - 记录**没有 `rubricSnapshot`**（旧记录、没有要点列表的题）：保持现在的校验，只要求 0 到满分，不加步长约束。例如步长 1、满分 6 的旧任务仍然可以确认 2.5 分。
- `isAuto: true` 时，服务端除了现在的开关和置信度校验，对**带 `aiPoints`** 的记录还要看逐点结果（没有 `aiPoints` 的记录只走现在的校验）：只要有一点 `verified` 为 false（引用没通过）、`disagree` 为 true（多次采样不一致）或 `missing` 为 true（模型漏判），就返回 403「这份有要点需要老师确认」。这条在服务端判断，所以不认识新字段的旧扩展在全自动下也会停下。

`GradingInfo` 新增字段：`points`（AI 的逐点结果，即 `aiPoints`）、`finalPoints`（老师确认的逐点得分，没确认或只改了总分时为 null）和 `rubric`（取自这条记录的 `rubricSnapshot`，包括分值、`allowPartial` 和汇总规则）。老师的评分记录列表、记录详情（`GET /api/records/:id`）和管理端记录接口都返回这三项，控制台据此逐点对比 AI 和老师的得分、高亮改过的点；`finalPoints` 为 null 而总分和 AI 不同时，显示为「只改了总分」。扩展拿到这两项就能画出逐点打分界面。

## 6. 面板交互

所有有要点列表的题，结果页都加一个「逐点打分」区：每个要点一行。

```
① 要点句……（2 分）          [满分] [半分] [0] [__]   AI：满分「学生原文片段」
② 要点句……（2 分）          [满分] [半分] [0] [__]   AI：半分 —— 只说了一半
③ 要点句……（3 分，可选）    [满分] [半分] [0] [__]   AI：0
                                      总分：5 / 6（按任意两点计）
```

- 每点给四个选择：满分、半分、0、自定义（输入框，范围 0 到该点分值，按步长取整）。半分 = 分值的一半按步长四舍五入，再夹到 [步长, 分值 − 步长]：2 分的点是 1 分，3 分的点（步长 1）是 2 分，5 分的点（步长 2）是 2 分。
- 不能给部分分的点（`allowPartial` 为 false，或分值不到两个步长，见第 4 节）只能给 0 或满分：不显示「半分」和自定义输入框，H 快捷键对它无效。面板、AI 解析（第 4 节）和服务端确认校验（第 5 节）用同一条规则，没有例外。老师确实想给这一点部分分时，去改要点列表，或者直接改总分（见下一条）。
- 总分随时按汇总规则重新计算。总分输入框仍然保留：老师直接改总分时，逐点区标成「已手动覆盖总分」，提交时只交总分，不交逐点。改总分是有意留下的出口，不受逐点规则约束，只受「0 到满分、步长整数倍，正好等于满分时例外」约束。总分输入框、确认接口和直接打分接口都用这同一条规则；没有要点列表的题，总分输入框保持现在的校验（只限 0 到满分）。
- 键盘：数字键 1–9 选中第几点；选中后 F 是满分，H 是半分，0 是零分；Enter 提交（和现在一样）。
- AI 的引用和理由放在每一行右侧，可以展开。校验没通过的引用标红。

### 各模式

| 模式 | 有要点列表 | 没有要点列表 |
| --- | --- | --- |
| 手动 | 新增「直接打分」按钮：不调用 AI、不扣次数，直接出现逐点打分区，全部为空，老师逐点选完提交。「获取建议分」仍然保留，想参考 AI 时再点 | 和现在一样 |
| 半自动 | 换卷后 AI 自动出逐点建议，老师逐点检查后提交。不一致或引用没通过的点标黄 | 和现在一样 |
| 全自动 | 照旧自动提交，并记下逐点结果。新增一条暂停条件：有任何一点引用校验失败或多次采样不一致，就停下等老师确认。服务端确认接口也会拒绝这种全自动提交（第 5 节），旧扩展同样停得下来 | 和现在一样 |

「直接打分」提交时没有 AI 记录，需要新接口 `POST /api/records/manual { taskId, image, rubricVersion, points?, modifiedScore? }`，建一条 `status=manual` 的记录。

- `rubricVersion` 是面板打开逐点表单时拿到的要点列表版本。服务端在同一个事务里核对它和任务当前的版本：
  - 一致：用这一版生成 `rubricSnapshot`，按它校验和算分。
  - 不一致（比如老师打分期间在另一个窗口改了分值或汇总规则）：返回 409「要点列表已更新，请重新加载后再打分」，不建记录。这样快照就一定是老师打分时看到的那一版。
- `points` 和 `modifiedScore` 的规则和确认接口完全一样：
- 只传 `points`：按快照校验并算总分。
- 只传 `modifiedScore`：老师覆盖了总分，`finalPoints` 留空。
- 两个都传：必须一致，否则 400。
- 两个都不传：400。

图片指纹仍然记录，避免同一份重复计入。这条记录不扣次数，也不进入自动学习的示例。这部分在 C 期，见第 9 节。

`status=manual` 是新状态，现有代码有不少地方按 `status = 'done'` 统计或查询，要逐一定下怎么处理：

| 地方 | `manual` 记录怎么算 |
| --- | --- |
| 题目的「已评 / 已确认」、组织成员的「已评分」、概览的评分量和每日趋势 | 算进去：老师确实阅了这一份。概览另外分开显示「其中直接打分 x 份」。同一张图（同一题、同一图片指纹）既有 AI 记录又有直接打分记录时只算一份，按最新确认的那条计 |
| 概览的 AI 指标（平均延迟、置信度、AI 与终分的偏差） | 不算：没有 AI 结果 |
| 同图缓存（`judge()` 复用上次结果） | 不算：没有 AI 结果可以复用。老师对同一张图先直接打分、又点「获取建议分」时照常调用 AI |
| 自动学习的示例 | 不算（同上文） |
| 确认接口 `POST /api/records/:id/confirm` | 不接受：直接打分建档时就已经确认了 |
| 老师的评分记录列表、控制台记录详情 | 显示，标「直接打分」，没有 AI 那一栏 |

实现时把这些查询从 `status = 'done'` 改成显式的状态列表，不依赖默认值，并为每一处补测试。

## 7. 控制台

- 阅卷任务页：每道题显示要点列表，可以编辑和确认，也可以「生成草稿」。没确认的草稿显示为「待确认」。
- 评分记录详情：逐点显示 AI 的判定、引用和老师的最终得分，改过的点高亮。
- 题目统计（新）：每个要点「AI 判分 vs 老师确认」的不一致率。哪一点总被改，说明这一点的表述或分值需要调整。

## 8. 兼容

- `/api` 只新增字段，不改已有字段：`GradingInfo` 加 `points`、`rubric`，确认接口加可选的 `points`，任务接口加 `rubricPoints`。旧扩展忽略这些新字段，照旧按总分确认；全自动下遇到需要老师确认的要点，由服务端返回 403 让它停下（第 5 节）。
- 旧任务没有要点列表时，提示词、解析、面板和确认接口的校验都和 0.3.0 一样。本设计新增的校验（步长整数倍、逐点拦截全自动）只作用在带 `rubricSnapshot` / `aiPoints` 的记录上。
- 新扩展遇到旧服务端时，`GradingInfo` 里没有 `rubric`，扩展就不显示逐点区，确认时也不发 `points`（旧服务端会以 400 拒绝不认识的字段，见第 5 节）。
- 加一个功能开关 `point_grading`（默认关）：先给部分用户或组织打开，看各点的改判率，再全量。

## 9. 分期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| A | 要点列表的数据结构、草稿生成、确认接口；面板「题目设置」和控制台任务页可以编辑和确认 | 一道语文题能生成草稿、改完确认、保存后不会被扩展的 upsert 覆盖 |
| B | 按要点评分的提示词（v5）和解析、`rubricSnapshot`、`aiPoints` 和 `finalPoints` 入库、确认接口加 `points`、面板逐点打分区（半自动、全自动） | 半自动下 AI 逐点给分，老师改其中一点，总分自动算，记录里逐点保存 |
| C | 手动「直接打分」（不调用 AI）、控制台记录详情逐点展示、每点改判率统计 | 手动模式不扣次数完成一份；控制台能看到每点的改判率 |

## 10. 已定的取舍

1. 手动模式做「直接打分」：不调用 AI、不扣次数，放在 C 期。
2. 「半分」取该点分值的一半，按步长四舍五入，再夹到 [步长, 分值 − 步长]：2 分的点是 1 分，3 分的点（步长 1）是 2 分。分值不到两个步长的点没有半分。
3. 汇总规则先只做 `sum` 和 `best n`；分组规则（如「观点 2 分 + 论据任选两点各 2 分」）先不做，遇到再加。
4. 这次只按语文问答题调提示词；理科分步给分以后再说。
